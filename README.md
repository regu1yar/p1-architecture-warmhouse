### 1. Описание функциональности монолитного приложения

**Сервисные возможности:**

- Админы / специалисты могут:
  - просматривать все датчики в системе
  - подключать в систему новые датчики
  - удалять датчики из системы
- Система поддерживает:
  - выдачу всех датчиков: `GET /api/v1/sensors/`
  - добавление датчика в систему: `POST /api/v1/sensors`
  - удаление датчика: `DELETE /api/v1/sensors/:id`
  - обновление метаданных датчика: `PUT /api/v1/sensors/:id`

**Управление отоплением:**

- Пользователи могут, если верить описанию задания, управлять отоплением (менять температуру на датчиках, что бы это ни значило) через веб-интерфейс.
  Однако в коде все управляющее воздействие завязано на обновление содержимого БД.
- Система поддерживает:
  - выставление таргетной температуры на заданном датчике
  - изменение статуса датчика
- Взаимодействие с бэкендом происходит через ручку `PATCH /api/v1/sensors/:id/value`. На самом деле ручка лишь записывает таргетную температуру и статус в БД.

**Мониторинг температуры:**

- Пользователи могут просматривать температуру на установленных в их домах датчиках через веб-интерфейс (по `id` датчика и по помещению)
- Система поддерживает:
  - получение показателя датчика (real-time данные только для температуры) - `GET /api/v1/sensors/:id`
  - получение температуры с датчика в заданном помещении - `GET /api/v1/sensors/temperature/:location` - судя по всему, параметр `location` может выступать ключом соответствующего датчика для внешнего API

### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Go
- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы (обработка запросов, бизнес-логика,
  работа с данными) находятся в рамках одного приложения. Выбор технологий ограничен языком Go.
- Взаимодействие: Синхронное, запросы обрабатываются последовательно.
- Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
- Развертывание: Требует остановки всего приложения. Используется docker-compose,
  для приложения написан Dockerfile.
- Зависимости: Описаны внутри конфигурационных файлов `go.*`.
- Отказоустойчивость: Низкая, ошибка в коде мониторинга температуры может привести к падению
  всего приложения и невозможности изменить температуру в помещении.
- Скорость разработки: Средняя, проект пока небольшой, но уже сейчас есть проблемы с
  тесной связью между компонентами системы. В частности, работа с внешним сервисом ведется напрямую через API без унифицированного интерфейса.

### **4. Проблемы монолитного решения**

- Ограниченная масштабируемость:
  - невозможно горизонтально масштабировать часть системы, находящейся под большей нагрузкой
  - внедрение асинхронного взаимодействия может требовать глобального рефакторинга
- Проблемы с отказоустойчивостью и развертыванием из-за единого приложения
- Смешение понятий и контекстов: устройства и датчики сливаются в одну сущность

# Задание 5. Работа с docker и docker-compose

Перейдите в apps.

Там находится приложение-монолит для работы с датчиками температуры. В README.md описано как запустить решение.

Вам нужно:

1) сделать простое приложение temperature-api на любом удобном для вас языке программирования, которое при запросе /temperature?location= будет отдавать рандомное значение температуры.

Locations - название комнаты, sensorId - идентификатор названия комнаты

```
	// If no location is provided, use a default based on sensor ID
	if location == "" {
		switch sensorID {
		case "1":
			location = "Living Room"
		case "2":
			location = "Bedroom"
		case "3":
			location = "Kitchen"
		default:
			location = "Unknown"
		}
	}

	// If no sensor ID is provided, generate one based on location
	if sensorID == "" {
		switch location {
		case "Living Room":
			sensorID = "1"
		case "Bedroom":
			sensorID = "2"
		case "Kitchen":
			sensorID = "3"
		default:
			sensorID = "0"
		}
	}
```

2) Приложение следует упаковать в Docker и добавить в docker-compose. Порт по умолчанию должен быть 8081

3) Кроме того для smart_home приложения требуется база данных - добавьте в docker-compose файл настройки для запуска postgres с указанием скрипта инициализации ./smart_home/init.sql

Для проверки можно использовать Postman коллекцию smarthome-api.postman_collection.json и вызвать:

- Create Sensor
- Get All Sensors

Должно при каждом вызове отображаться разное значение температуры
